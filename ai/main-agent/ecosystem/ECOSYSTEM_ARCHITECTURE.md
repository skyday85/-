# Экосистема организации — архитектура 1.1

## Роль Главного агента

Главный агент — центральный оркестратор всей цифровой экосистемы организации. Он не является агентом одного приложения и не принадлежит финансовому модулю или автопарку. Его задача — принимать управленческие поручения пользователя, выбирать нужные специализированные агенты и приложения, объединять результаты и контролировать сквозные процессы.

Главный агент не заменяет базы и бизнес-логику приложений. Он получает контролируемые данные через API/инструменты, связывает их, делегирует работу специализированным агентам и журналирует действия.

## Иерархия агентов

Главный агент находится над специализированными агентами. Первоначальный набор:

1. Агент «Закупщик» — подбор запчастей, каталоги, применяемость, запросы поставщикам, предложения, закупка.
2. Агент «Сборщик писем» — отдельный подчинённый агент для получения, первичного разбора, классификации и маршрутизации входящих писем и вложений. Он не принимает окончательные финансовые или управленческие решения; результаты передаются Главному агенту.
3. Финансовый агент/контур — банковские операции, счета, ДДС, классификация, план/факт, дебиторка/кредиторка и финансовая аналитика.
4. Агент продаж — лиды, сделки, клиенты, коммерческие предложения, заказы, воронка и повторные продажи.
5. Маркетинговый агент — каналы привлечения, кампании, лидогенерация, стоимость привлечения, эффективность и маркетинговая аналитика.
6. В дальнейшем подключаются другие специализированные агенты по тому же контракту.

Специализированные агенты не должны напрямую координировать друг друга в обход Главного агента для сквозных операций. Главный агент сохраняет контекст бизнес-кейса, определяет порядок вызовов и собирает итоговый результат.

## Приложения экосистемы

1. Управление автопарком — техника, эксплуатация, ТО, ремонты, топливо, документы, запчасти, закупки и история.
2. Финансы и планирование — банк, ДДС, расчёты, дебиторка/кредиторка, бюджеты, план/факт, календарь платежей и финансовая аналитика.
3. Продажи и маркетинг — маркетинговые касания, лиды, клиенты, сделки, заказы, каналы привлечения и продажи.
4. Почтовый/документный контур — входящие письма и вложения как источник событий, счетов, запросов клиентов, предложений поставщиков и других документов.
5. Будущие приложения подключаются через тот же интеграционный контракт.

## Главная сквозная цепочка

Маркетинг → первое касание → лид → сделка → заказ → исполнение → автопарк/ресурсы → документы → оплата → финансы → прибыль → повторная продажа.

## Сквозная цепочка закупки запчастей

Поручение пользователя → Главный агент → Закупщик → поиск в доверенных каталогах → проверка применяемости → запрос/предложение поставщика → счёт → Сборщик писем/документный контур → распознавание счёта → подтверждение классификации → финансовый учёт → закупка/получение → установка на автомобиль → расход и история автомобиля.

## Дополнительные бизнес-процессы

### Клиентский цикл
Первое обращение → квалификация → предложение → договор → заказ → выполнение → закрывающие документы → оплата → дебиторка → повторная продажа → история клиента.

### Исполнение заказа
Заказ → требования → назначение ресурсов/автомобиля → выполнение → фактические показатели → подтверждение → закрытие.

### Экономика заказа
Выручка → прямые затраты → использование техники → прочие затраты → распределённые затраты → маржа/результат заказа.

### Закупочный цикл
Потребность → заявка → подбор → предложения → выбор → заказ → счёт → оплата → поставка → приёмка → использование/установка → закрывающие документы.

### Денежный цикл
Начисление/счёт → дебиторка/кредиторка → банковское движение → распределение → сверка → остатки → прогноз.

### Планирование
Годовая цель → квартал → месяц → задачи/KPI → факт → отклонение → причина → предложение корректировки → согласование → контроль исполнения.

### Инциденты и качество
Проблема/жалоба/поломка/задержка → инцидент → причина → последствия → ущерб → корректирующее действие → контроль → закрытие.

### Документооборот
Письмо/договор/заявка/счёт/закрывающий документ → распознавание → классификация → связь с клиентом, заказом, закупкой, автомобилем и платежом → архив → контроль отсутствующих документов.

### Управление ресурсами
Автомобили, сотрудники, оборудование и другие ресурсы → назначение → использование → загрузка → затраты → эффективность.

### Риски и отклонения
Обнаружение → оценка → причина → ответственное лицо → действие → срок → контроль → закрытие.

### Управленческое решение
Сигнал → сбор фактов → варианты решения → оценка последствий → решение пользователя → задача → исполнение → проверка результата.

## Сквозные идентификаторы

Каждое приложение сохраняет собственные ID, но передаёт их Главному агенту в стандартном интеграционном формате:

- business_case_id — сквозной кейс/цепочка бизнеса;
- customer_id — клиент;
- lead_id — лид;
- deal_id — сделка;
- order_id — заказ;
- execution_id — исполнение;
- vehicle_id — техника;
- counterparty_id — контрагент;
- invoice_id — счёт;
- transaction_id — банковская операция;
- purchase_id — закупка;
- email_id — письмо;
- attachment_id — вложение;
- campaign_id — маркетинговая кампания;
- task_id — задача;
- incident_id — инцидент;
- plan_item_id — элемент плана.

## Business Case

`business_case_id` связывает события разных приложений и агентов в одну логическую цепочку. Он не заменяет локальные идентификаторы.

Пример продажи:
маркетинговое касание → lead_id → deal_id → order_id → execution_id → vehicle_id → invoice_id → transaction_id → итоговая экономика.

Пример закупки:
потребность автомобиля → purchase_id → запрос поставщику → email_id → invoice_id → transaction_id → получение → установка → vehicle_id → итоговый расход.

Главный агент должен уметь восстановить всю цепочку по business_case_id и показать источники данных, пропуски, расхождения и итоговый результат.

## Правила интеграции

1. Приложения остаются владельцами своих данных.
2. Главный агент не пишет напрямую в их БД.
3. Специализированные агенты получают только разрешённые инструменты своего домена.
4. Доступ идёт через версионируемые API/инструменты.
5. Каждая запись содержит `source_system`, `source_record_id`, время изменения и при необходимости `business_case_id`.
6. Неуверенные связи не подтверждаются автоматически — они получают статус `needs_review`.
7. Финансовая классификация на начальном этапе требует подтверждения пользователя согласно правилам финансового контура.
8. Существенные управленческие изменения требуют согласования пользователя.
9. Все действия агентов журналируются с указанием `agent_id`, `action`, источника и результата.
10. Каждый агент и приложение поддерживают общий контракт внешнего Security Control, но не имеют доступа к опасным функциям безопасности.

## Цель

Главный агент должен анализировать и координировать бизнес от первого маркетингового контакта до продажи, исполнения, закупок, документов и фактического финансового результата, одновременно контролируя автопарк, ресурсы, риски, отклонения и качество данных между приложениями.
