# ADR-002: Главный агент как control plane экосистемы

Статус: принято для реализации.

## Решение

Главный агент является control plane всей экосистемы. Он не хранит предметные данные приложений и не заменяет их сервисы. Каждое приложение остаётся самостоятельным владельцем данных, API и бизнес-правил.

Главный агент состоит из пяти основных слоёв:

1. **Project Registry** — список всех приложений и репозиториев, их доменов, API-контрактов, статуса и разрешений.
2. **Agent Registry** — специализированные агенты и их способности.
3. **Connector Layer** — версионируемые API-клиенты к приложениям.
4. **Orchestration Layer** — бизнес-кейсы, делегирование, межпроектные цепочки, планирование и контроль.
5. **Audit & Policy Layer** — проверка полномочий, журналирование и ограничения действий.

## Репозитории

Текущие доступные репозитории:
- `skyday85/-` — временное место реализации Главного агента и прототипов почты;
- `skyday85/fleet-management` — автопарк;
- `skyday85/finance-planning` — финансы и планирование.

Целевые новые репозитории:
- `skyday85/main-agent`;
- `skyday85/mail-service`.

Создание целевых репозиториев и перенос выполняются отдельно. До переноса архитектура должна оставаться совместимой с выделением без изменения API-контрактов.

## GitHub access broker

Главный агент не хранит постоянный GitHub token. Доступ к GitHub выдаётся через отдельный backend broker / GitHub App.

Политика:
- deny by default;
- чтение только зарегистрированных репозиториев;
- запись только при явном праве проекта;
- запись только в рабочие ветки;
- прямой write в `main`, `master`, `production`, `prod` запрещён;
- секреты, приватные ключи и `.env*` недоступны для записи;
- удаление репозитория, rewrite history и изменение защиты веток недоступны;
- каждая операция журналируется.

GitHub permissions минимальные: Metadata/Contents/Pull Requests/Checks/Actions read; Contents/Pull Requests write только для режима разработки и только через policy layer.

## Доступ к приложениям

Доступ к репозиторию не равен доступу к production-данным приложения. Production-операции выполняются только через бизнес-API приложения с отдельной авторизацией.

Главный агент не должен:
- выполнять SQL напрямую в production БД приложения;
- читать OAuth-токены почтового сервиса;
- читать секреты CI/Vercel;
- обходить пользовательское подтверждение, если оно требуется бизнес-правилом.

## Сквозные операции

Каждая межпроектная операция получает:
- `business_case_id`;
- `source_system`;
- `source_record_id`;
- `initiator`;
- `agent_id`;
- `correlation_id`;
- `created_at`.

Оркестратор хранит ссылки и состояние процесса, но не дублирует исходные бизнес-данные приложений.

## Следующие этапы

1. Завершить реестр проектов и policy layer.
2. Выделить `main-agent` в самостоятельный репозиторий.
3. Выделить `mail-service`.
4. Настроить GitHub App / broker и выдать минимальные права на зарегистрированные репозитории.
5. Подключить коннекторы fleet, finance и mail.
6. Добавить единый журнал межпроектных действий.
7. Добавить планировщик и business-case orchestration.
